# CLAUDE.md — boilerplate-astro

Boilerplate personnel, pour les sites de contenu. Les conventions générales sont dans `~/.claude/CLAUDE.md`, la spécification commune dans `boilerplates-commun/SPEC-COMMUNE.md` (section 21 pour ce dépôt) : ce fichier ne note que les choix propres au projet.

## Choix du projet

- **Type** : Astro 7, rendu serveur à la demande par `@astrojs/node` (mode `standalone`). Les pages sans donnée sont pré-rendues (`export const prerender = true`).
- **Composants** : couche Svelte de `@kewinmarchand/boilerplates-ui` (ADR 0004 de la bibliothèque), par `@astrojs/svelte`. Sans directive `client:*`, un composant Svelte est **rendu sur le serveur sans JavaScript** : c'est le cas par défaut. Seuls les éléments interactifs sont des îlots hydratés. Toute la bibliothèque passe par la façade `@/shared/ui/kit` (règle ESLint).
- **Architecture** : celle de `boilerplates-commun/ARCHITECTURE-DDD.md` (D1 à D12). Couche de routage `src/pages/` (un fichier par route, qui délègue), `src/views/`, `src/modules/<module>/{domain,application,infrastructure,ui}`, `src/shared/`. Règles de dépendance vérifiées par ESLint (`@boundaries/eslint-plugin`), comme dans boilerplate-svelte.
- **Alias** : `@/` vers `src/` (standards front), jamais de chemin relatif au-delà d'un niveau.
- **CSS** : Tailwind 4 sur le préréglage des jetons de la bibliothèque, avec la feuille de thème de boilerplate-svelte (`src/shared/theme/theme.css` : jetons, composants, police Inter, variantes `js:` et `no-js:` sur la classe `js` posée par le script d'amorçage). Les composants d'interface de SvelteKit (header, menus, bascules, carrousel) sont repris tels quels, ce qui évite de réécrire leur style.
- **Icônes** : sprite `public/icons.svg` tiré de Lucide, généré par `make icons` depuis `icons.json`, avec le type des noms `src/shared/ui/kit/iconNames.ts`. Un seul composant, `@/shared/ui/kit/Icon.astro`. `make icons-check` (dans `make qa`) échoue si le sprite ou le type sont périmés.
- **Îlots** : bascules du thème et du mode renforcé en `client:load` ; menu mobile en `client:media="(max-width: 1023.98px)"` (aucun JavaScript sur desktop) ; carrousel en `client:visible`. Les composants Svelte repris de SvelteKit reçoivent en propriété ce que SvelteKit lisait dans `$app/state` (chemin courant).
- **Amorçage** : `BaseLayout.astro` pose un script inline (`is:inline`) qui ajoute la classe `js`, puis applique le mode renforcé et le thème mémorisés avant le premier rendu.
- **Image LCP** : Astro ne remonte pas le `<svelte:head>` d'un composant Svelte rendu sur le serveur. Le préchargement passe par `ImagePreload.astro` (façade `kit`), placé par la vue dans le slot `head` du layout ; `ResponsiveImage.svelte` ne garde que l'image.
- **Images** (ADR 0002 de l'API Platform) : les photos de contenu (produits, articles) viennent de l'API. `ResponsiveImage` et `ImagePreload` reçoivent l'objet `image` du contrat (`ImageView`, `src/shared/ui/kit/image.ts`), `null` ne rend aucune image (fond neutre pour la carte produit). Seul le hero reste dans `public/images/` : `staticImage` construit le même objet depuis `<nom>-<largeur>.<ext>`. L'image de partage d'une page de catalogue est la plus grande variante WebP du premier produit (`largestWebp`). La CSP autorise l'origine de l'API en `img-src`.
- **Fiche article** (section 2 bis de la spec commune) : `src/pages/blog/[slug].astro` charge `loadArticle` (`modules/blog/index.server.ts`, `GET /api/articles/{slug}`) ; slug inconnu, `Astro.rewrite('/404')` comme les pages légales ; API en panne, titre de repli et message (`article-error`). `ArticleView.astro` passe par `PageLayout` (fil d'Ariane Accueil › titre, `headingTestId`), avec `publishedTime` (`og:type` article), l'image de partage (`largestWebp`), son préchargement (`ImagePreload`) et le JSON-LD `BlogPosting`. Le texte en HTML reprend la classe `prose-legal`. Fiches dans le sitemap (`listArticlePaths`), cartes de l'accueil en lien étiré sur le titre.
- **SEO** : fonctions pures de `@/shared/seo` reprises de SvelteKit ; `SeoHead.astro` les rend dans le `<head>` du layout (Astro ne remonte pas `<svelte:head>`). `PageLayout.astro` calcule fil d'Ariane et métadonnées d'une seule source, puis rend le fil et le `<h1>`. Les pages pré-rendues reçoivent leur chemin avec une barre finale : `toAppPath` la retire (canonique et fil d'Ariane).
- **Erreurs** : `src/pages/404.astro` et `500.astro` (vue `@/views/errors`). Route de test de la 500 : `/erreur-test` (Astro ignore les fichiers de `src/pages/` préfixés par `_`), 404 hors dev sauf `DEV_ROUTES=1`. Maintenance : `MAINTENANCE=1` dans `src/middleware.ts`, 503 et `Retry-After`.
- **API** (spec commune, section 6) : appelée sur le serveur pendant le rendu, par le client typé `@/shared/api/client` (`openapi-fetch`, types générés par `make api-types` dans `schema.d.ts`), seulement depuis la couche `infrastructure/` des modules. `API_URL` (8090 API Platform par défaut, 8091 Hono) est lu à l'exécution. Le `X-Scenario` de la requête (tests e2e) est porté jusqu'au client par un `AsyncLocalStorage` posé par le middleware (`withRequestScenario`), l'équivalent du `getRequestEvent` de SvelteKit : les dépôts n'ont pas à recevoir la requête.
- **Menu des catégories** : chargé une fois par requête par le middleware (`Astro.locals.categoryMenu`, typé dans `src/env.d.ts`), lu par le layout et le plan du site. Les pages ne sont donc pas pré-rendues (le menu serait figé au build, et l'image Docker n'a pas d'API à ce moment) : seul `robots.txt` l'est, et le middleware ne fait rien pour une page pré-rendue.
- **Catalogue** : domaine, application et infrastructure repris de boilerplate-svelte. La route `src/pages/catalogue/[...slugs].astro` appelle le cas d'utilisation puis délègue à `CatalogPage.astro`, qui calcule titre, fil d'Ariane et SEO (`describeCatalogPage`, fonction pure) et rend la vue Svelte en îlot (`client:load`). Contrat de l'API (ADR 0005 de l'API Platform) : `findCatalogListing` lit en parallèle `GET /api/products` (une page, tableau de `Product` : filtres, tri, page) et `GET /api/product-facets` (total et compteurs, mêmes filtres sans tri ni pagination) ; `toListing` calcule le nombre de pages depuis `totalItems` (au moins une). Filtres, tri et pagination naviguent par le **routeur client d'Astro** (`ClientRouter`, posé seulement sur les pages du catalogue ; `navigate()` remplace le `goto` de SvelteKit). L'îlot est conservé d'une page à l'autre (`transition:persist`) et reçoit les nouvelles données : le focus reste sur le champ de filtre ou de tri manipulé, et revient au titre après un lien (pagination, Tout effacer). Le routeur remplace les attributs de `<html>` : le script d'amorçage se rejoue sur `astro:after-swap` (classe `js`, mode renforcé, thème).
- **Grille de page** : un îlot (`<astro-island>`, `display: contents`) enfant direct de `main.page-grid` laissait ses enfants hors de la colonne de contenu ; `theme.css` applique aussi la règle à `astro-island > *`.
- **Menu de catégories** (desktop) : îlot `client:media="(min-width: 1024px)"`, lien simple vers le catalogue sans JavaScript.
- **Serveur de production** : l'adaptateur Node d'Astro ne compresse rien (SvelteKit, lui, précompresse ses fichiers statiques) ; sans compression, le catalogue tombait à 0,85 sur Lighthouse. Adaptateur en mode `middleware` et `server.mjs` : fichiers de `dist/client` servis dans la variante précompressée acceptée (`.br`, puis `.gz`, écrites au build par l'intégration `tools/precompress.ts`), cache d'un an sur `/_astro/` (noms versionnés), puis rendu par Astro. Les pages HTML sont compressées à la volée par le middleware (`@/shared/http/compressHtml`). `make start`, Playwright, Lighthouse et l'image Docker passent tous par `server.mjs`.
- **Tâches** : îlot qui charge la liste dans le navigateur (`useTasks`, chargement, erreur avec relance, liste vide) ; l'adresse de l'API, lue sur le serveur, lui est passée en propriété. TanStack Query, qui ne se partage pas entre îlots, est remplacé par ce hook. L'API doit autoriser l'origine du site en CORS : 4321, 3170, 3171 et 3270 ajoutés aux deux API le 31/10/2026.
- **Contact** : Astro Actions (`src/actions/index.ts`, `accept: 'form'`, schéma zod du domaine). Sans JavaScript, le formulaire envoie un `POST` natif et la page rend le résultat (`Astro.getActionResult`, valeurs saisies relues dans la requête). Avec JavaScript, l'îlot valide chaque champ au blur et appelle l'action sans recharger la page. Le cas d'utilisation `submitContactMessage` traduit les violations 422 de l'API en erreurs de champ et un échec en message neutre.
- **Blog** de l'accueil : rendu sur le serveur sans hydratation (contenu pour le SEO), « Réessayer » recharge la page.
- **Carrousel de l'accueil** : produits « À la une » lus dans l'API par le module `catalog` (`GET /api/featured-products`), cochés dans l'admin des produits : `src/pages/index.astro` appelle `loadFeaturedProducts` (`index.server.ts`) et passe le résultat à `FeaturedProducts.astro`, qui monte l'îlot `ImageCarousel` (`client:visible`). En erreur : message à la place des diapositives ; sans produit à la une, la section disparaît. `ImageCarousel` (socle, sans métier) reçoit un `href` facultatif par diapositive : le titre devient un lien étiré sur toute la diapositive (`carousel-slide-link`, `draggable="false"`) ; après un glisser, Embla annule le clic (test e2e).
- **Fiche produit** (section 11 bis de la spec commune) : `src/pages/produit/[slug].astro` charge `loadProduct` (`GET /api/products/{slug}`, union `success`, `error`, `not-found`) ; slug inconnu, `Astro.rewrite('/404')`. `ProductView.astro` : fil d'Ariane Catalogue › catégories de `categoryPath` (chemins construits par `toProductDetail`), JSON-LD `Product` avec `Offer`, description construite, image de partage = plus grande variante WebP, image LCP préchargée. Le sitemap ajoute les fiches (`listProductPaths`, liste lue par pages de 48 jusqu'à une page incomplète). Les cartes du catalogue portent un lien étiré sur le nom (`catalog-product-link`).
- **Produits similaires** (section 11 bis) : `SimilarProducts.astro` du module `catalog`, après l'`<article>` de la fiche, appelle `loadSimilarProducts` (`GET /api/products?category=…&itemsPerPage=9`, sans le produit affiché, 8 au plus) et monte `ImageCarousel` (`client:visible`). Liste vide ou API en erreur : la section disparaît, la fiche reste servie.
- **Panier** (section 11 ter) : module `cart` en forme réduite, sans API. Domaine pur (`addItem`, `setQuantity`, `removeItem`, `countItems`, `totalPrice`, plafond 99), stockage `localStorage` clé `panier` (`cartStorage.ts`, lecture validée à la main : le lien du header est sur chaque page, zod alourdirait son îlot ; mémoire de repli si le stockage refuse l'écriture, événement maison dans l'onglet, `storage` entre onglets). Chaque îlot (lien, bouton, page) lit le panier au montage par `useCart` (vide au rendu serveur, `ready` faux jusqu'au montage). Le socle ne connaît pas le panier : le middleware pose `CartLink.astro` (qui monte l'îlot en `client:idle`) dans `Astro.locals.cartLink`, rendu par le header ; `src/pages/produit/[slug].astro` passe `AddToCartButton` (`client:load`) au slot `purchase` de `ProductView`. `/panier` est `noindex`, hors du sitemap, avec un `<noscript>` rendu sur le serveur ; Playwright coupe les scripts sans afficher les `<noscript>` : le test lit le message dans le HTML servi. Nom accessible du lien composé du texte visible et de compléments masqués (axe refuse un `aria-label` qui ne contient pas le texte affiché).
- **Pages légales** (ADR 0001 de l'API Platform) : lues dans l'API par le module `content` (`GET /api/legal_pages/{slug}`), administrées dans son `/admin`, comme le blog : la route appelle `loadLegalPage` (`index.server.ts`) et passe le résultat à la vue. Pages légales : `<h1>` tiré du titre de l'API (prop `heading` de `PageLayout`, titre SEO et fil d'Ariane inchangés), sections rendues par `LegalPageContent.astro`, dont le HTML est injecté par `set:html` sans autre filtre (l'API échappe le HTML saisi et retire les liens dangereux), stylé par `.prose-legal` (`theme.css`, liens au rendu de `.bui-link`). API en panne : titre de repli et message ; page inconnue de l'API : `Astro.rewrite('/404')`. Restent dans le front : la section « Mesure d'audience » et la case d'opposition (Matomo), et l'état de conformité du lien du footer (`SITE.accessibility`).
- **Observabilité** (section 16 de la spec commune) : configuration lue **à l'exécution** sur le serveur (`PUBLIC_GLITCHTIP_DSN`, `PUBLIC_GLITCHTIP_ENVIRONMENT`, `PUBLIC_MATOMO_URL`, `PUBLIC_MATOMO_SITE_ID`) et rendue par le layout dans un bloc JSON (`#observability-config`), lu par le script `@/shared/observability/client` : les `PUBLIC_*` d'Astro seraient figés au build côté navigateur. Sans variable, rien n'est chargé. GlitchTip : `@sentry/astro` importé dynamiquement après l'affichage (navigateur) ou à la première erreur (serveur, middleware), sans donnée personnelle ni trace ; 404 et scénarios de test exclus. Matomo sans cookie (`disableCookies` en premier), une page vue au chargement puis à chaque navigation du routeur client (`astro:after-swap`), refus de la mesure lu avant toute commande (case d'opposition sur la page Données personnelles, section affichée seulement quand Matomo est activé).
- **CSP** : `Content-Security-Policy-Report-Only` posé par le middleware sur chaque page, calculé à l'exécution par `@kewinmarchand/csp` (via `@/shared/security`, origines de l'API, de Matomo et de GlitchTip seulement si renseignées), route `POST /api/csp-report`. Ligne de démarrage `[boilerplate-astro] serveur démarré (<environnement>)` au chargement du middleware.
- **Charte graphique** : `/charte-graphique`, vue `@/views/styleguide` reprise de SvelteKit (sections Svelte en un îlot, qui lit les jetons calculés), 404 hors dev sauf `DEV_ROUTES=1`, lien discret dans le footer en dev.
- **URL publique** : `SITE.url` lit `PUBLIC_SITE_URL` à l'exécution (repli sur `site` d'Astro, figé au build) : une image Docker construite sans la variable publiait sinon des URL en `localhost:4321`. Accès par `globalThis.process`, la config étant aussi importée par des îlots.
- **Action et îlot** : passer l'action elle-même (`actions.contact`) en propriété d'un îlot la fait appeler pendant le rendu serveur (`ActionCalledFromServerError`, page pourtant en 200) : on passe son adresse, `String(actions.contact)`.
- **Grille de page** : `main.page-grid` remplit la hauteur de la fenêtre ; `align-content: start` garde les rangées en haut sur une page courte (404, tâches), sinon elles se partagent la hauteur.
- **Unité de police** : `px`.
- **Langue** : français uniquement, URL en français.

## Ports et conteneurs

- Dev 4321 (`make up`), e2e 3170 (Playwright, dans le conteneur), Lighthouse 3270 (section 7 de la spec commune).
- Seuls prérequis : Docker avec Compose, `make` et git. Le service `node` (image officielle Playwright à la version exacte de `@playwright/test`) porte Node, Yarn et Chromium, dépendances dans le volume nommé `node_modules`. `ASTRO_TELEMETRY_DISABLED=1` dans les conteneurs.
- Image de production : `Dockerfile` multi-étapes sur Node 26 Alpine (même version majeure que l'image de dev ; Node 26 ne livre plus Yarn, installé par npm dans l'étape `base`, absent de l'image finale), `node dist/server/entry.mjs` sur le port 3000.

## Règles de lint propres au projet

- `no-restricted-imports` : bibliothèque, icônes, client d'API, Embla, SDK GlitchTip et CSP ne s'importent que dans leur wrapper du socle ; le domaine et l'application n'importent aucun framework (`astro`, `astro:*`, `@astrojs/*`, `svelte`).
- `boundaries/dependencies` : routage → vues, index public des modules, socle ; vues → index public des modules, socle ; un module n'importe jamais un autre module ; le socle n'importe ni module, ni vue, ni routage ; couches d'un module selon ARCHITECTURE-DDD.
- Auto-test des règles (`make arch-selftest`, dans `make qa`) : écrit chaque violation à son emplacement réel, dont une dans un composant `.astro`, exige l'échec d'ESLint avec le message attendu, puis retire le fichier.
